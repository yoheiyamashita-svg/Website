# コーディングコメントに関する絶対要件

このプロジェクトは、単に動作するWebアプリを作ることだけが目的ではない。
開発者自身がコードを読みながら、JavaScript、Canvas API、物理モデル、数値計算、UI実装を学習できる教材としても利用する。

そのため、生成するすべてのコードについて、以下のコメント規則を必ず守ること。

## 1. 使用したライブラリ・API・組み込み関数の意味をコメントする

外部ライブラリ、Web API、Canvas API、JavaScriptの重要な組み込み関数・メソッドを使用する場合、その直前または同一ブロック内に、

- 何をする関数・APIなのか
- なぜこの場所で使用するのか
- 引数には何を渡しているのか
- 戻り値は何を意味するのか

を日本語コメントで記述する。

```javascript
// requestAnimationFrameは、ブラウザが次の画面を描画する直前に
// 指定した関数を実行するWeb API。
// setIntervalよりも画面描画と同期しやすいため、アニメーションに使用する。
requestAnimationFrame(animationLoop);
```

Canvas APIについても同様にする。

```javascript
// beginPath()はCanvas上で新しい描画パスを開始する。
// これを呼び出しておくことで、前回描画した線と今回の線が
// 意図せず接続されることを防ぐ。
ctx.beginPath();
```

ただし、明らかに自明なコードすべてにコメントを付けて冗長化する必要はない。
「そのコードを初学者が見たとき、何をしているのか分かりにくいか」を基準にコメントする。

## 2. 数式には必ず物理的意味をコメントする

物理シミュレーションに関係する数式をコードに記述する場合、

1. 数式
2. 各変数の意味
3. 単位
4. その式が表している物理現象
5. なぜこの計算を行うのか

をコメントで説明する。

```javascript
// 波数 k [rad/m]。
// 波長 λ [m] に対して、1波長あたりの位相変化を表す。
// k = 2π / λ
const waveNumber = 2 * Math.PI / wavelength;
```

## 3. 物理量には単位を明記する

物理量を扱う変数については、可能な限りコメントで単位を明示する。変数名だけでは単位が分からない場合は必ずコメントで補足する。

## 4. 数式とコードの対応を明確にする

物理公式を実装するときは、「教科書上の式」→「コード上の変数」→「計算結果」の対応が分かるようにする。

## 5. JavaScriptの文法についても必要に応じて説明する

初学者が理解しにくい構文（class, constructor, export/import, async/await, arrow function, destructuring, map/filter/reduce, spread syntax, optional chaining, callback, requestAnimationFrame等）は、「なぜこの書き方をしているのか」が分かりにくい箇所を優先して説明する。すべてに逐一付ける必要はない。

## 6. Canvas座標系について説明する

画面座標と物理座標の変換を行うコードには、必ずその意味をコメントする。

```javascript
// 物理座標 x [m] をCanvas上の画面座標 X [px] に変換する。
// scale は「1 mを何pxで表示するか」を表す。
// X = originX + x × scale
const canvasX = originX + physicsX * scale;
```

## 7. 「なぜそうするのか」を優先してコメントする

単なる処理説明ではなく、理由を説明する。

## 8. 物理モデルと描画処理を混ぜない

Physics Layerのコメントでは物理的意味を説明する。Renderer LayerのコメントではCanvas・描画上の意味を説明する。役割を分ける。

## 9. コメントだけでなくJSDocも使用する

再利用するクラス、関数、物理モデルについてはJSDocを積極的に使用する。

```javascript
/**
 * 正弦進行波の変位を計算する。
 *
 * 物理式:
 *   u(x,t) = A sin(kx - ωt + φ)
 *
 * @param {number} x - 初期位置 [m]
 * @param {number} time - 時刻 [s]
 * @param {WaveParameters} parameters - 波のパラメータ
 * @returns {number} 変位 u [m]
 */
function calculateDisplacement(x, time, parameters) {
  // ...
}
```

## 10. コメントと実装を常に一致させる

コメントに書いた数式と実際のコードの計算が一致していなければならない。物理モデルを変更した場合は、関連するコメント・JSDoc・README・テストも更新する。「コメントだけ古い状態」のままにしない。

## 11. AIによる実装時の禁止事項

以下は禁止する。

- 意味の説明がない複雑な数式を突然コードに書く
- 外部ライブラリ/APIを使っているのに説明しない
- 数値計算の根拠を説明しない
- 変数名だけで物理量を推測させる
- コメントと実装が異なる状態を放置する
- 「magic number」を理由なくコード中に直接書く

```javascript
// 悪い例
const y = x * 200;

// 良い例
// 物理座標[m]をCanvas座標[px]に変換する。
// 1m = 200pxとして表示する。
// 将来的に画面サイズに応じて変更できるようscaleとして管理する。
const canvasY = x * scale;
```

## 12. コメントの言語

コメントは原則として日本語で記述する。変数名・関数名・クラス名は英語とする。

## 13. 教材として読めるコードを目指す

「短く書けるから短く書く」よりも、「物理とプログラムの対応が理解しやすい」ことを優先する。ただし、意味のない冗長なコメントや重複コードは避ける。

## 14. 実装前の確認

コードを生成する前に、使用するAPI・数学関数・物理公式・変数の意味・単位・数式とコードの対応を確認する。特にPhysics Layerでは、「この計算はどの物理式に対応しているか」を説明できる状態にしてから実装する。

## 15. 完成時のコードレビュー

各Stageの実装完了時に、以下を確認する。

- [ ] 主要な物理式にコメントがある
- [ ] 物理量の単位が分かる
- [ ] Canvas APIの重要な処理に説明がある
- [ ] 重要なJavaScript APIに説明がある
- [ ] 数式とコードの対応が分かる
- [ ] 座標変換の意味が分かる
- [ ] 「なぜこの処理をしているのか」が分かる
- [ ] コメントと実装が一致している
- [ ] 初学者がコードを追える

> 「コメントを大量に付けてほしい」のではなく、「コードを読めば物理とプログラムの対応関係が理解できる状態にしてほしい」
